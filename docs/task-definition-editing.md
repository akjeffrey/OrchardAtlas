# Editing task definitions (#77–#79)

Open a task checklist and use the edit control beside its name. Start dates are editable for one-time and repeating tasks. End dates remain optional and cannot precede the start. Changing start updates open work in the current occurrence and the future recurrence schedule; completed/skipped/cancelled history and its activity dates are retained. Earlier occurrence memberships are frozen. Current completion records stay attached to the same occurrence identity so changing a date does not duplicate completed entries.

Task targets offer Whole orchard (one general checklist entry), Group / Type / Variety (automatic matching per plant and seasonal planting), or Choose individual plants. Group, Type and Variety are optional successive filters. Individual checkbox choices override automatic criteria: added outliers stay included, exclusions stay excluded, and newly matching plants join automatically. Changing target mode resets individual overrides (manual mode starts from the current matching selection). Active plants/current seasonal plantings can be added; Area/Row scopes already configured on tasks can be retained. Removing an open current member hides it but keeps a membership record; reselecting it through the editor restores the same record. Completed members remain visible in their recorded occurrence. Per-entry trash deletion remains final for that occurrence and does not disable future repeats.

**Delete entire task** is available on the edit page, including for empty groups and completed tasks. Confirmation explains that open entries and future repeats are removed, reminders/calendar exports are cleared, and completed history and recorded plant activities are retained. The parent definition uses a deletion marker, preventing regeneration after restart, offline edits or backup restore. Per-entry trash continues its separately confirmed behavior. Unrelated tasks, plants and independent activities are unchanged.

## Domain and persistence

`TaskPlan` adds optional manual inclusion/exclusion target keys (`p:<UUID>`, `c:<UUID>`, `s:<UUID>`), legacy member IDs, a deletion flag and schedule identity fields. Lists are bounded to 400 explicit overrides each; matching plants still join dynamically. Existing plans/assignments default these fields without migration. Editing an old standalone or group task attaches a definition through `legacyIds`, retaining original task and activity IDs rather than rewriting completed records.

`taskOccurrences` separates display start dates from stable occurrence keys. A changed repeating schedule retains the current occurrence key, assigns a new UUID schedule generation, and creates UUIDv5 keys for later occurrences. This prevents date collisions when reanchoring to an earlier or much later year. `generateFrom` prevents edited criteria from inventing historical memberships. Display labels use actual task dates, not identity keys. Existing date-based keys remain valid. `membershipExcluded` marks open members removed through the editor without discarding their identity or falsely completing/skipping them.

Domain changes are calculated before repository submission. Local definitions and entries persist in one snapshot and are included in Drive archives. Firestore submits bounded batches with the parent definition in the first batch; local submission does not wait for network acknowledgement, and server errors use the existing write-failure reporting. Large connected changes spanning multiple batches can briefly appear partially updated while cache snapshots arrive; completion history is protected by the rules. Concurrent edits follow existing last-write behavior. Deploy the updated Firestore rules before using connected editing.

Reminder/calendar projections index parent/member links and calculate each schedule once per group, reuse unchanged records, use the latest active definitions, omit deleted/excluded work and normalize legacy links in memory. Current calendar completion counts use the revised schedule while original plant events keep their original dates. Future reminders and calendar occurrences use the revised recurrence anchor. Calendar upload timing still depends on the phone's calendar adapter. No credentials or new native permissions are required.
